PART 2 — ⚠⚠ DEPLOY SAFETY — READ BEFORE TOUCHING AN EDGE FUNCTION

This section exists because of what happened this week.

On 7 and 10 August two fixes were deployed to ghl-order-push: the customer welcome email (v30) and the fix that lets GHL's dialler ring a customer (v29). Some time before 13 August, versions v31–v34 were deployed from an older copy of the file. Both fixes were silently wiped. Nobody noticed for a week.

The cost: about 40 customers received no welcome email — no terms, no 15-year warranty, no care sheets. Clause 3 of the Terms promises the comfort guarantee by email on confirmation of sale, so this was a contractual gap, not a courtesy.

The rules that follow from it

R1. ALWAYS READ THE LIVE FUNCTION BEFORE YOU DEPLOY OVER IT. Fetch the deployed source, diff it against what you are about to send, and account for every line you are removing. Never paste from a chat, a note or a memory of what it used to contain.

R2. EVERY CRITICAL FUNCTION CARRIES A "DO NOT REMOVE" HEADER. ghl-order-push now opens with a numbered list of the five blocks that must never disappear, each with the fault it fixes. Add to that list whenever something important goes in. If a header block ever disappears, that is the regression.

R3. A SILENT FAILURE IS A BUG, EVEN WHEN THE CODE "WORKS". The welcome email was written to tolerate a missing document URL — log a warning and send anyway. Reasonable, and exactly how it hid. Anything that can quietly do nothing must either shout (console.error) or report what it did. ghl-order-push now returns an attached list naming the documents that actually went. Check it after any change.

R4. IF IT MATTERS, PROVE IT IN THE DATA, NOT THE CODE. ghl_pushed_at is set on only 4 of 571 orders — that single query would have caught this in seconds at any point in the week. For anything that must happen on every order, know the column or table that proves it happened.

R5. VERIFY verify_jwt AFTER EVERY MCP DEPLOY. Redeploying through the MCP can flip it. Check it matches what the function needs, every time.

R6. AFTER DEPLOYING, READ IT BACK. Fetch the function again and confirm what you intended is actually there.

The weekly two-minute check (do this every Monday)

-- Welcome emails: should be roughly one per order taken.
select date(created_at at time zone 'Pacific/Auckland') as day,
       count(*) as orders, count(ghl_pushed_at) as emails_sent
from sim_orders
where created_at > now() - interval '14 days'
  and coalesce(order_status,'active') <> 'cancelled'
group by 1 order by 1 desc;

If emails_sent is materially below orders on any day, something is broken.

The amount is read server-side from the payment ledger — never from the iPad's request. What a customer is told they paid must be what was recorded.

3.2 How the email is now timed — and why

The cash panel sits on the Done screen, so the email must not go the instant the order finishes or cash would always miss it. It now works like this:

  1. At Done, the iPad pushes the GHL contact with contactOnly: true. The

contact exists immediately — the office is never left waiting — but no email goes.

  1. If cash is recorded, that releases the email straight away, with the

amount in it.

  1. Otherwise, the database job sweep_welcome_emails() sends it. Runs every

5 minutes; picks up any finished order still unsent after 4 minutes.

The sweeper is what makes this safe. Closing the app, losing signal or a dead battery cannot lose the email any more. The send-once claim (sim_orders.ghl_pushed_at) is taken atomically inside the edge function, so the iPad and the sweeper can never both send.

⚠ The sweeper is deliberately limited to orders from the last 24 hours. Do not widen that window without deciding what to do about the backlog first — see 5.1.

3.3 Cash at the door (built yesterday, unchanged today)

Solicited sales only. Green "💵 Cash received" panel on the Done step. The box starts empty with Full amount / 50% quick-fill buttons, and the amount is confirmed twice — cash has no gateway, no receipt and no bank feed, so the only record is what the consultant types.

Behind it, record_cash_at_sale() — only the consultant named on that order or the office; refuses an unsolicited sale, a negative amount, or more than the sale value; writes a real payment row and rebuilds the paid total from the ledger, never adding to it.

3.4 Ezidebit — the iframe is gone

The eDDR form used to sit in a fixed 900×2100 iframe scaled to fit. When Ezidebit's final step fell below that height the customer never reached the page that reports back — so the account was created and the order flagged incomplete. The whole page now goes to Ezidebit and comes back. There is no frame to size. A resume marker (2-hour expiry) carries the order, the customer, the schedule and the PDF payload across the trip.

⚠ Anything finalizeOrder needs must travel in that resume marker, because the page reloads mid-order now. Missing customerId cost us the rewards QR code on the first live order after the change.

Every Ezidebit return is now logged to ezidebit_callback_log — read that table first if a direct debit ever fails to attach.

3.5 Arrears — the "behind" figure was wrong

The chase list was flagging customers who were up to date. Two causes, both fixed in the single view v_order_position:

  • The schedule start recorded on the order matched the customer's **first real

debit on only 82 of 349 orders** — median 14 days early, so "expected by now" counted debits that were never due. It now anchors on the first real debit attempt.

  • Ezidebit settles ~2 working days after it debits, so money in transit read as

arrears. It now measures to the latest settlement date, not today.

Plus a silence check — no payment for more than two periods — which catches a customer who has stopped paying even when the dates flatter them, and which now ignores anyone carrying more than two instalments of credit.

Chase list went from 127 to 76. 29 rows were removed from the arrears text sequence: 25 on track and paying, 4 whose orders are closed.

⚠ The same calculation used to exist in three places and had drifted. It now lives once, in the database.

PART 6 — HOW THINGS ACTUALLY WORK

An order reaches the system two ways. From the iPad (Sales App), or from the QR code / paper form, which creates a GHL contact that is imported. Both end at ghl-order-push, which is why the welcome email lives there — it is the one place that sees every order exactly once.

The office is told at Done, not before. The order is inserted as draft at step 7 and only promoted to pending when it reaches Done. Two separate paths used to announce it mid-sale — the live banner and the GHL staff text — and both were moved.

Delivery clearance is one view, v_delivery_clearance. A customer needs a clean run of payments and 10% of contract value. On a 156-week term, eight weekly payments is about 5% — so the 10% rule, not payment behaviour, is what usually holds an order back. 33 well-paying customers were individually authorised on 13 August; the rule itself is unchanged.

Arrears position is one view, v_order_position. Anchored on the first real debit, measured to the last settled payment date.

Scheduled jobs go through cron_call → cron-dispatch, which mints a single-use token so no secret is ever written into cron.job. Targets are on an allow-list. The welcome-email sweeper uses this path.

PART 7 — GOTCHAS WORTH KEEPING

  • A 200 response is not a success — check the body.
  • Check the test before believing it. One run said 36 pages were failing; the

test waited 1.2 seconds for a 2.4-second timeout.

  • cron.job_run_details looks alarming until you compare it to now(). A

job that "hasn't run" is often a job that isn't due for another 40 minutes.

  • iOS keeps separate storage for Safari and a Home Screen app. Pair from the

icon, not from Safari. And a Home Screen app serves a stale page for days — kill it from the app switcher.

  • current_date in the database is UTC. Anything day-based in the NZ morning

reports the previous NZ day. Pass an explicit NZ date.

  • RAISE NOTICE output is invisible through the MCP — collect results into a

temp table and select it.

  • The SQL editor has no auth.uid() — impersonate with

set_config('request.jwt.claims', …) or every security-definer function will say "not signed in".

  • **A catch-all exception when others that does not RECORD is how a real fault

hides for weeks.** Three were found in two days.

  • loyalty_config.value is NUMERIC. Anything with words needs its own table.
  • Null is not false. The visible error is often not the fault.
  • **When Nigel says "we spent a lot of time on this" — search the past

conversations before concluding anything.** Two hours were lost this week hunting for something that was documented in an earlier session.
